Runbook · Inbetriebnahme

Umzug nach Databricks

Von der leeren Arbeitsumgebung bis zum laufenden Wochenjob, der die VDE-Regelwerkszugänge selbst verwaltet. Zehn Phasen, jede mit einem Abnahmekriterium — was nicht abgenommen ist, wird nicht weitergereicht.

Gesamtaufwand
2–3 Tage
Laufzeit
2–3 Wochen
Phasen
10
Blockierend

Der kritische Pfad

Die Technik ist an einem Tag erledigt. Der Zeitplan hängt an drei Dingen, die nicht von dir abhängen — deshalb gehören sie in die erste Stunde, nicht in die erste Woche.

  • 01 Netzwerkfreigabe zum Portal Ausgehend HTTPS vom Cluster zur Normenbibliothek. Blockiert Phase 3. 1–2 Wochen
  • 02 Qualität der SharePoint-Liste Jede Unsauberkeit wird später zu einer Aktion im Portal. Blockiert alles ab Phase 5. offen
  • 03 Lizenzvertrag prüfen Deckt der VDE-Vertrag automatisierten Zugriff mit technischem Konto? Blockiert Phase 7. Einkauf

Phasen

    Phase 0Tag 1 · 1 Stunde

    Anstoßen, was Vorlauf braucht

    Drei Anträge, die parallel zu allem anderen laufen.

    WasAn wenKonkret
    Ausgehender Netzzugang zum PortalNetzwerk-Admin HTTPS/443 zur Portal-Domäne. Bei Azure: Regel für das Workspace-Subnetz
    App-Registrierung mit Sites.SelectedEntra-ID-Admin Anwendungsberechtigung plus Admin-Zustimmung. Ablaufdatum des Secrets notieren
    Freigabe der App auf die SiteSharePoint-Admin Leserecht auf genau diese eine Site — Sites.Selected wirkt erst dadurch

    Parallel selbst entscheiden

    • Katalog und Schema. Vorschlag governance.vde_zugang.
    • Dienstkonto für den Job. Ein Service Principal, nicht dein Benutzer — sonst steht der Job still, sobald dein Passwort rotiert.
    • Technisches Konto im Portal. Dann ist im Portal-Protokoll erkennbar, was automatisiert passiert ist.
    Vertragsfrage

    Ob automatisierter Zugriff mit technischem Konto vom VDE-Lizenzvertrag gedeckt ist, entscheidet der Einkauf, nicht die IT. Antwort abwarten, bevor Phase 7 scharf geschaltet wird.

    Phase 1Tag 1 · 45 Minuten

    Grundgerüst im Workspace

    Repository als Git-Ordner einbinden

    databricks repos create \
  --url https://github.com/<owner>/<repo> \
  --provider gitHub \
  --path /Workspace/Repos/vde-zugangsverwaltung

    Katalog, Schema und Volumes anlegen

    CREATE CATALOG IF NOT EXISTS governance;
CREATE SCHEMA  IF NOT EXISTS governance.vde_zugang;

CREATE VOLUME IF NOT EXISTS governance.vde_zugang.konfig;
CREATE VOLUME IF NOT EXISTS governance.vde_zugang.screenshots;

    Berechtigungen setzen

    Das Schema enthält Name, Personalnummer und E-Mail von Mitarbeitern. Der eng gefasste Zugriff ist keine Formalie — er ist der Grund, warum der Datenschutz später zustimmen kann.

    GRANT USE CATALOG ON CATALOG governance TO `<dienstkonto>`;
GRANT USE SCHEMA, CREATE TABLE, MODIFY, SELECT
  ON SCHEMA governance.vde_zugang TO `<dienstkonto>`;
GRANT READ VOLUME, WRITE VOLUME
  ON VOLUME governance.vde_zugang.konfig TO `<dienstkonto>`;
    Abnahme

    SELECT * FROM governance.vde_zugang.INFORMATION_SCHEMA.TABLES läuft ohne Fehler durch.

    Phase 2Tag 1 · 20 Minuten

    Zugangsdaten hinterlegen

    Nichts davon gehört in den Code oder in ein Notebook.

    databricks secrets create-scope vde-zugang

# SharePoint / Microsoft Graph
databricks secrets put-secret vde-zugang graph-tenant-id
databricks secrets put-secret vde-zugang graph-client-id
databricks secrets put-secret vde-zugang graph-client-secret

# VDE Normenbibliothek
databricks secrets put-secret vde-zugang portal-benutzer
databricks secrets put-secret vde-zugang portal-passwort

# Lesezugriff für den Job
databricks secrets put-acl vde-zugang <dienstkonto> READ
    Kalendereintrag jetzt

    Client Secrets in Entra ID laufen ab, meist nach 12 oder 24 Monaten. Ein abgelaufenes Secret ist die häufigste Ursache, wenn ein solcher Job nach einem Jahr plötzlich stillsteht.

    Abnahme

    dbutils.secrets.get("vde-zugang", "graph-tenant-id") liefert einen Wert. Angezeigt wird [REDACTED] — das ist richtig so.

    Phase 3Tag 1 · 45 Minuten

    Cluster mit Browser

    Serverless scheidet aus

    Der Job braucht Chromium samt Systembibliotheken. Serverless-Compute lässt weder Init-Scripts noch apt-Installationen zu. Es wird ein klassischer Single-Node-Job-Cluster.

    Init-Script ins Volume legen

    databricks fs cp resources/init_playwright.sh \
  dbfs:/Volumes/governance/vde_zugang/konfig/init_playwright.sh

    Cluster anlegen

    EinstellungWert
    Cluster-ModusSingle Node
    Runtime15.4 LTS
    ZugriffsmodusSingle User → das Dienstkonto
    KnotentypAzure Standard_DS3_v2 · AWS m5d.large · GCP n2-standard-4
    Init-ScriptVolume → …/konfig/init_playwright.sh
    UmgebungsvariablePLAYWRIGHT_BROWSERS_PATH=/opt/playwright
    Auto-Terminierung20 Minuten

    Der Browser braucht Arbeitsspeicher. Unter 14 GB wird es eng, sobald die Benutzerliste mehrere hundert Zeilen hat.

    Rauchtest

    from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    b = p.chromium.launch(args=["--no-sandbox"])
    seite = b.new_page()
    seite.goto("https://<portal-domaene>")
    print("Titel:", seite.title())
    b.close()
    Abnahme

    Der Seitentitel der Normenbibliothek erscheint.

    Timeout statt Titel → die Netzwerkfreigabe aus Phase 0 ist noch nicht durch, nicht der Cluster ist schuld. Startet Chromium gar nicht, hat das Init-Script nicht gegriffen: Cluster-Ereignisprotokoll → Init script logs.

    Phase 4Tag 2–8 · offen

    SharePoint-Anbindung und Datenqualität

    Die Phase, die in der Praxis am längsten dauert. Nicht wegen der Technik, sondern weil die gewachsene Liste selten so sauber ist, wie man denkt.

    Ersten Lauf als reinen Lesetest fahren

    WidgetWert
    portal_modusaufgabenliste
    dry_runtrue
    mail_versandaus

    Es wird nichts geschrieben, nichts versendet, das Portal nicht angefasst.

    Abschnitt 6 des Notebooks abarbeiten

    Dort stehen die Datenqualitäts-Hinweise: fehlende Personalnummern, fehlende E-Mail-Adressen, doppelte Zeilen, Mitarbeiter ohne Regelwerk, abgelaufene Soll-Einträge. Die Personalnummer ist der Schlüssel zwischen Liste und Portal — ist sie im Portal nicht gepflegt, muss die E-Mail-Adresse auf beiden Seiten identisch sein.

    Abnahme

    Die Warnliste ist leer, oder jeder verbleibende Eintrag ist bewusst so gewollt und dokumentiert. Diesen Schritt nicht abkürzen: Jede Unsauberkeit hier wird später zu einer Aktion im Portal.

    Phase 5Tag 8 · 1–2 Stunden

    Portal-Selektoren ermitteln

    Der einzige Schritt mit echter Handarbeit — und der einzige, der nach einem Portal-Update wiederholt werden muss. Auf dem eigenen Rechner ausführen, nicht auf dem Cluster: mit --sichtbar verfolgst du im Browserfenster mit, was passiert.

    pip install playwright && playwright install chromium

python3 scripts/selektoren_erkunden.py \
    --url https://<portal-domaene> \
    --benutzer <technisches-konto> \
    --passwort '...' \
    --sichtbar \
    --ausgabe selektoren.json

    Das Skript läuft Anmeldung, Benutzerübersicht und Anlegen-Formular ab und schlägt Kandidaten vor. Am Ende listet es auf, was es nicht gefunden hat — typischerweise die Zellenselektoren und die beiden Vorlagen:

    {
  "zelle_personalnummer": "td.personalnummer",
  "zelle_regelwerke": "td.lizenzen",
  "auswahl_regelwerk": "input[data-regelwerk=\"{regelwerk}\"]",
  "knopf_regelwerk_entziehen":
      "tr[data-pnr=\"{personalnummer}\"] button.entfernen"
}

    Zwei Regeln beim Ergänzen

    1. Stabile Merkmale bevorzugen. id, name und data-* überleben ein Portal-Update meist, CSS-Klassen oft nicht.
    2. Der Entzugsknopf muss auf die Zeile eingegrenzt sein. Ohne tr[data-pnr="{personalnummer}"] davor trifft er die falsche Person. Dafür gibt es einen Test: test_entziehen_trifft_nur_die_richtige_person.
    python3 -m unittest discover -s tests -v   # 58 Tests

databricks fs cp selektoren.json \
  dbfs:/Volumes/governance/vde_zugang/konfig/selektoren.json
    Abnahme

    Der Job startet ohne Selektor-Fehler. Fehlt ein Pflichtfeld, verweigert er den Start und nennt die offenen Felder — statt stillschweigend nichts zu tun.

    Phase 6Tag 9 · 1 Stunde

    Lesen ohne Schreiben

    Die wichtigste Stufe. Hier zeigt sich, ob die Selektoren stimmen.

    WidgetWert
    portal_modusbrowser
    dry_runtrue
    selektoren_pfad/Volumes/governance/vde_zugang/konfig/selektoren.json
    screenshot_pfad/Volumes/governance/vde_zugang/screenshots

    Der Job meldet sich am Portal an, liest den Bestand, rechnet die Maßnahmen aus — und ändert nichts.

    Wenn die Zahlen nicht stimmen

    SymptomUrsache
    Benutzerzahl weicht abZeilenselektor oder Blätterfunktion falsch
    Regelwerke fehlen oder sind zerhacktzelle_regelwerke oder Trennzeichen falsch
    Personalnummern leerfalsche Zellenspalte
    Nicht weitergehen

    Öffne das Portal parallel im Browser und vergleiche Benutzerzahl und Stichproben mit dem, was der Job anzeigt. Solange der gelesene Ist-Bestand nicht exakt zum Portal passt, nicht weiter — ein falsch gelesener Bestand erzeugt in Phase 7 falsche Aktionen.

    Phase 7Tag 10 · 2 Stunden

    Erster Echtlauf, klein gehalten

    Notbremse enger stellen

    WidgetErster LaufSpäter
    max_entzuege210
    max_aenderungen540
    dry_runfalsefalse

    Löst die Notbremse aus, ist das kein Fehler, sondern die richtige Reaktion — sieh dir an, warum so viele Änderungen anstehen.

    Protokoll ansehen

    SELECT stichtag, status, aktion, name, regelwerk, meldung, dauer_s
FROM governance.vde_zugang.massnahmen
ORDER BY erstellt_am DESC;
    Abnahme

    Alle Aktionen stehen auf ERFOLG, sind im Portal sichtbar, das Protokoll ist vollständig. Der Job liest zwar selbst nach — beim ersten Mal willst du es trotzdem mit eigenen Augen gesehen haben.

    Bei FEHLER: Meldung und Screenshot im Volume ansehen. Fast immer ist es ein Selektor, der auf einer Unterseite anders heißt als auf der Übersicht.

    Phase 8Tag 11 · 1 Stunde

    In Produktion nehmen

    databricks bundle validate
databricks bundle deploy -t prod

    Variablen in resources/vde_zugangsabgleich_job.yml vorher füllen: portal_url, sp_site_hostname, verantwortlicher, dienstkonto, node_type.

    Zeitplan aktivieren

    pause_status von PAUSED auf UNPAUSED setzen und erneut ausrollen. Montags 07:00 Europe/Berlin.

    Alarmierung

    Die Job-Benachrichtigung deckt nur den Absturz ab — nicht den Fall, dass der Job sauber durchläuft und die Notbremse gezogen hat. Dafür ist die Ergebnismail da: Der Betreff beginnt dann mit LAUF GESTOPPT. Eine Postfachregel darauf lohnt sich.

    Abnahme

    Ein manuell ausgelöster Lauf über die Job-Oberfläche läuft grün durch und die Mail kommt an.

    Phase 9dauerhaft

    Betrieb und Rückfall

    Wöchentlich, 5 Minuten

    Ergebnismail lesen. Interessant sind zwei Zeilen: fehlgeschlagen und offen. Prüffälle abarbeiten — der Teil, der bewusst bei dir bleibt.

    Monatlich, 15 Minuten

    SELECT aktion, status, count(*) AS anzahl
FROM governance.vde_zugang.massnahmen
WHERE stichtag >= current_date() - INTERVAL 30 DAYS
GROUP BY ALL ORDER BY anzahl DESC;

    Häufen sich FEHLER bei einer bestimmten Aktion, hat sich das Portal geändert.

    Wenn sich das Portal ändert

    Erkennbar an Klartext-Meldungen wie „Benutzerübersicht nicht gefunden". Der Job ändert dann nichts, er bricht ab.

    1. selektoren_erkunden.py erneut laufen lassen
    2. Geänderte Felder ersetzen
    3. python3 -m unittest discover -s tests
    4. Neue selektoren.json ins Volume
    5. Einmal mit dry_run = true gegenprüfen

    Realistisch ein- bis zweimal im Jahr, Aufwand je unter einer Stunde.

    Rückfall

    SituationMaßnahme
    Portal geändert, keine Zeit für Selektoren portal_modus = aufgabenliste — du bekommst wieder die Aufgabenliste per Mail und klickst selbst
    Etwas ist grundsätzlich falsch Zeitplan auf PAUSED

    Ein Rückbau der Datenlage ist nie nötig: Die Wahrheit steht im Portal, die Delta-Tabellen sind Protokoll und Momentaufnahme.
